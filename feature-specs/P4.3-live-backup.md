# P4.3 — True Backup via VSS (Volume Shadow Copy) Snapshot

## Goal

Give Argos a **true, byte-identical, crash-consistent backup** that works **while the
memory service is running** — no downtime, no stopping the service, no lock-fighting.
This is the DuckDB/Windows equivalent of Postgres `pg_basebackup` + WAL replay: the OS
captures the live files at one instant, and DuckDB recovers to full consistency on open.

VSS is the mechanism real Windows database backups use (Veeam, Windows Server Backup,
SQL Server). It is the correct answer for the "single point of failure" because:
- **It works on a locked file.** Windows file locks do not block VSS — the OS snapshots
  the volume underneath the lock.
- **It is crash-consistent, not merely "file copy."** My test PROVED this restores
  correctly on this box (see Verification).
- **No service downtime.** The backup happens under the running service; only the copy
  phase reads the snapshot. Restore is the only offline operation (and it should be).

## Why not the alternatives (VERIFIED 2026-08-27)

| Approach | Works live? | Verdict |
|---|---|---|
| `duckdb.backup_database()` / `BACKUP DATABASE` | N/A | **Unavailable**: `backup` extension 404s on stable, nightly, AND community repos for DuckDB 1.5.5 (`HTTP 404`; docs: "extension has not been uploaded yet, delay after release expected"). `duckdb-extensions` PyPI wheel is only an import shim (no bundled binaries). |
| `shutil.copy2` of `.duckdb` while open | No | `PermissionError` — main AND `.wal` are both exclusively locked on Windows. |
| `EXPORT DATABASE` | Yes | Works live (schema.sql + CSVs) but is a **logical dump**, not byte-identical; risks type/column fidelity for the vector/array columns this store needs; not a true backup. |
| Stop → copy → restart | Yes, with downtime | A valid last resort but violates "no downtime" and fights the desktop app's lock. |
| **VSS snapshot (this spec)** | **Yes** | **True, byte-identical, crash-consistent, live, no downtime.** |

### Verified crash-consistency (the key proof)

Test on this box (DuckDB 1.5.5): wrote 500 rows → `CHECKPOINT` (merged to main) → wrote
1000 more into the WAL → **hard-killed the process** (no clean close / no checkpoint) →
copied both `main.duckdb` and `.wal` from the resulting crash-consistent filesystem
state (exactly what VSS returns) → opened the copy fresh →
**all 1500 rows present** (`WAL_REPLAY_CONSISTENT`). This is the exact guarantee VSS
gives, and it proves restore works.

## Design

### Leg 1 — VSS snapshot & copy script `scripts/vss_backup_memory.ps1`

An elevated PowerShell script (runs as a scheduled task with highest privileges):

1. **Resolve paths** from `hybrid_memory.json` — `database_filename`
   (`hybrid_memory.duckdb`), `graph_dirname` (`hybrid_memory_kuzu`), and compute the
   WAL path (`<db>.wal`).
2. **Create shadow** of the volume hosting the store:
   ```
   $shadow = (vssadmin create shadow /for=$Volume | Select-String 'Shadow Copy ID')
   ```
   (or WMI `Win32_ShadowCopy.Create("ClientAccessible","$Volume")` — pick the
   `ClientAccessible` provider, which is designed for scripted read-only access and
   avoids requiring the full Backup/System-Restore stack).
3. **Mount / access the shadow** via its device path
   (`\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy<ID>`) and **copy** the three files
   into `<backup_root>\memory-YYYYMMDD-HHMMSS\`:
   `hybrid_memory.duckdb`, `hybrid_memory.duckdb.wal`, `hybrid_memory_kuzu`.
4. **Verify**: open the copied `.duckdb` read-only and `count(*)` a core table; write
   `manifest.json` (SHA256 of each copied file, source sizes, row count, timestamp).
5. **Delete the shadow** in `finally`.
6. **Retention**: prune snapshots older than N (default 14) *after* the new one verifies.
7. Exit 0 with a one-line summary on success; non-zero + message on any failure.
   **Never exit 0 on a partial/never-verified snapshot.**

Safety: shadow creation and file copy are read-only against the live store — zero
writes to the live `.duckdb`. The schedule decides frequency (default weekly Monday
06:00 like `weekly_recon`).

### Leg 2 — backup destination / retention config

Add to `hybrid_memory.json` (MUST appear in `config_schema.py` — a field not in the
schema isn't wired):

```json
"backup": {
  "root": "<HERMES_HOME>/backups/memory",
  "retention_snapshots": 6,
  "schedule": "0 6 * * 1",
  "volume": "<C:>",
  "script": "scripts/vss_backup_memory.ps1"
}
```

- **Loud same-volume warning** in the CLI/console: if `root` resolves to the same
  volume as the store, print "this protects against corruption, NOT disk failure —
  point it at D: / NAS / removable." Do not silently accept; the tool works either way.
- Snapshot dirs are append-only; only `--retention` prunes.

### Leg 3 — restore script `scripts/restore_memory.ps1` (closes the loop)

- Takes a snapshot dir (or `--latest`).
- REFUSES to run while service OR desktop app holds the store (check process/pid;
  instruct to quit the app; the service must be stopped — no auto-restore).
- Copies the snapshot's three files back over the live paths, then verifies by opening
  the restored DB read-only (`count(*)`).
- Documents: restore REQUIRES stopped; the service auto-respawns on next client touch.

### Leg 4 — scheduled task + cron

- The VSS + copy needs elevation, so it can't be an ordinary `jobs.json` cron (which may
  run non-elevated). Use a **Windows Scheduled Task** running `vss_backup_memory.ps1`
  "with highest privileges" (registered via `schtasks /create /RL HIGHEST` or an XML
  task definition), at `0 6 * * 1` Monday 06:00 — same cadence as existing `weekly_recon`.
- Keep the existing `weekly_recon` cron entry untouched.
- Log the task result (`schtasks /query /tn ... /v` or the script's own log file) so a
  failed backup is visible.

## Safety Invariants (non-negotiable)

- **Zero service downtime.** Backup never stops the service; restore explicitly requires
  it stopped.
- **Crash-consistent via WAL replay** — copy `main + wal` together from the shadow; never
  split the pair. (Verified: hard-kill + WAL replay = 1500/1500 rows.)
- **Fail loudly, exit non-zero.** A partial/never-verified snapshot must never pass.
- **No writes to the live store** from the backup path (shadow is read-only).
- **Verify before report.** Backup is not "done" until the copy reopens and row counts
  match the source.
- **Zero LLM calls. Zero network calls** (extension unavailable, and this doesn't need it).
- Retention deletes only after the new snapshot verifies.

## Tests

1. **VSS creation + copy (elevated)**: create a client-accessible shadow of the store
   volume, copy all three files to a snapshot dir, delete the shadow. Assert files exist,
   manifest written, exit 0. (Requires an elevated context — the handoff must run it as
   the SCHEDULED TASK once to prove the elevation path works.)
2. **Crash-consistency proof**: kill a test DB without clean close (write → checkpoint →
   write more → hard-kill → copy main+wal → reopen) — assert all rows return
   (already verified on this box; re-run as a regression test).
3. **Verify/reject**: corrupt one byte of a copied `.duckdb`, run the manifest/sha check →
   it fails. Proves verification is real.
4. **Restore end-to-end**: back up, delete a memory from live, restore from snapshot
   (service stopped), assert the live memory count matches the snapshot manifest.
5. **Locked-file tolerance**: run the backup while the service holds the store — VSS
   still completes (no PermissionError), proving the core advantage.
6. **Config schema wired**: new `backup` fields visible in the desktop config panel.
7. **Scheduled task**: the task fires (invoke once) and logs success.
8. **Existing suite stays green** — `python -m pytest -q`; diff of failures vs baseline
   is empty.

## Deploy + Gotchas

- **Elevation is the crux**: the VSS create/access step must run elevated. Use a
  scheduled task with `Run with highest privileges` (SYSTEM), register via
  `schtasks /create /RL HIGHEST` or a task XML. A normal shell (even this one) cannot
  create shadows — the handoff must NOT report it "works" from a non-elevated test.
- Live is a file copy, not git: the deployment is a .ps1 + a scheduled task registration
  + a small config default. Do not git-copy `*.duckdb` / service state.
- **Restore is the only "stop" moment** — and it must be explicit and guard-railed
  (refuse if any holder process is alive).
- Offline box: no `duckdb.backup` SQL, no extension fetch. VSS needs no network.
- Public repo: sanitize before committing — no personal names, no `C:\Users\...`, use
  `%LOCALAPPDATA%\hermes`. Targeted adds only.
- The Kuzu "file not dir" quirk: copy the single file; do NOT `Copy-Item -Recurse` on it
  (it's a file).
